## Architecture decisions worth knowing before touching this code

### 1. Portal-based floating UI is load-bearing — don't regress it

Sidebar tooltips, the profile hover-pill, the notification dropdown, and the profile dropdown all render via `createPortal(..., document.body)` with `position: fixed` and coordinates computed from the trigger's `getBoundingClientRect()`.

This isn't decoration — it fixes a **confirmed, reproduced bug**: the sidebar and top-bar pill-nav are `rounded-full` capsules sized by shrink-to-fit (`width: auto`). When a hover tooltip/dropdown was nested *inside* one of those capsules as a normal `position: absolute` child, Chromium let the tooltip's width leak into the capsule's own auto-width calculation — hovering a sidebar icon made the whole capsule balloon from 62px to 150px wide. Verified numerically via `getBoundingClientRect()` before/after; fixed by moving all four to portals.

**Rule for any new floating UI (new dropdown, new tooltip, new popover) added later: never nest it inside a shrink-wrapped flex/glass container. Portal it to `document.body` and position it via a measured rect, following the existing pattern in `TopBar.jsx` (`ProfileTrigger`) and `Sidebar.jsx` (`NavButton`).**

Related gotcha already fixed once: if the anchor rect is measured only on mount (not on window resize), resizing the browser window desyncs the portaled element's position. `ProfileTrigger` in `TopBar.jsx` has a `resize` listener for this — copy that pattern, don't cache a rect without it.

### 2. Shell navigation is deliberately split across two surfaces

- **Top bar** (`TopBar.jsx`): a centered pill-tab bar (3-column CSS grid: logo / tabs / icons) holding the "primary" modules — Inicio, Workspace, Objetivos, Clientes, Finanzas. No background/border of its own; it blends into the page (per explicit user feedback — an earlier version had its own glass background and the user said it looked like "a rectangle" separating from the page).
- **Sidebar** (`Sidebar.jsx`): a floating rounded capsule (not a full-height panel) holding the remaining modules — Calendario, Conocimiento, Comunidad, Chat, News, Directorio — plus ADOR IA below a divider. Calendario moved here from the top bar on 2026-08-14 (user's own call, made by pointing at the sidebar in a screenshot) — no other reasoning recorded beyond that preference.

This split came from direct user reference images (a pill-tab nav bar + a separate floating icon capsule), not from the original written spec, which originally put all 10 modules in one full-height sidebar. If asked to add a new module, ask which surface it belongs on rather than assuming.

### 3. Design tokens live in `src/index.css`, reused everywhere

- `.ador-glass` — the standard card/surface recipe: `background: rgba(255,255,255,0.05)`, `border: 1px solid rgba(255,255,255,0.1)`, `backdrop-filter: blur(24px) saturate(160%)`, `box-shadow: 0 4px 24px rgba(0,0,0,0.3)`. Apply to every new card/dropdown/panel.
- `.ador-grain` — a 0.03-opacity SVG-noise `::after` overlay, paired with `.ador-glass` on almost everything.
- `.ador-skeleton` — a shimmer-sweep gradient (not a static dash) for values with no data yet. Added specifically because plain "—" placeholders made the Home screen feel dead; the shimmer reads as "the system is tracking this, just waiting on data."
- Keyframes: `ador-drift` (slow background gradient drift, Welcome screen), `ador-pulse` (opacity breathe, used for live-status dots and breathing icons), `ador-spin-dot` (6-dot loading ring), `ador-shimmer` (skeleton sweep).
- Color roles: bg `#0A0A0A`, text `#F5F5F5` / `#888888` / `#444444`, accent blue `#1E5FAD` (primary/brand), accent gold `#B8860B` (used sparingly — decisions/checkmarks only).

### 4. Firebase is guarded against missing config

`src/firebase.js` exports `isFirebaseConfigured` and only calls `initializeApp`/`getAuth` if `VITE_FIREBASE_API_KEY` is set. `useAuth.js` checks `auth` for null before every call. This was deliberate: the Firebase SDK throws synchronously on an invalid API key, which would otherwise white-screen the whole app if `.env` is ever missing. Preserve this pattern if Firestore gets wired in — `db` in `lib/firestore.js` already follows the same guard.

### 5. The `?preview=1` URL param is a dev-only test harness — not for shipping

`App.jsx` has a `PREVIEW_MOCK_USER` that bypasses Splash/Login/Welcome and injects a fake authenticated user (with a fabricated `displayName` and `lastSignInTime`) when the URL has `?preview=1`. This exists purely so Claude's own screenshot-based preview tooling could visually verify the authenticated shell without doing a real Google OAuth round-trip each time. It's harmless (real users won't stumble onto it), but don't rely on it as a real auth bypass, and consider removing it before any real deployment.

### 6. Welcome screen logic (`useWelcomeScreen.js`)

Shows on: first login of the day, or returning after 13:00 when the last login was before 13:00 same day. Tracked via `localStorage` keys `ador_last_login_at` and `ador_welcome_shown` (keyed by date + time-block so it never repeats within the same block). If this logic ever needs to change, the block boundaries (`morning` 6–13, `lunch` 13–15, `afternoon` 15–19, `evening` 19–6) are in that file.

### 7. Finance lives on Home now, Finanzas module later — deliberately not merged into Clientes

User asked (2026-08-14) where a financial overview for founders should live, and specifically floated combining it with Clientes. Decision: keep them separate *as modules/UI*. Clientes is a CRM/relationship model (client status, intervention progress); finance is a money-flow model (revenue, eventually expenses/runway) — different mental models that get harder to scan together as both grow.

However, they share one *data* source of truth on purpose (revised same day once Clientes actually got built — see §8): `FinanceBlock.jsx` on Home computes its monthly revenue, % change, and sparkline by reading `pago1`/`pago2` fields off every `clients/{id}` doc, not a separately-entered collection. An earlier version of this used a standalone hand-entered `revenue` collection — that was retired specifically to avoid a dual-source-of-truth problem (see §8's "why payments live on the client doc" for the reasoning). When a full Finanzas module gets built, it should read the same `pago1`/`pago2` fields for quarterly/annual rollups — never re-introduce a parallel manually-entered ledger.

### 8. Clientes module (2026-08-14) — SPC→SP pipeline CRM

Built from a detailed user-supplied spec (ADOR's internal vocabulary: SPC = Strategic Partner Candidate, SP = Strategic Partner once "Intervención Activa" starts; never "cliente"/"prospecto" in UI copy — see `lib/clientStages.js` for the full pipeline stage list). Lives at `src/components/clientes/`, wired into `AppShell.jsx` for the `clientes` nav item.

**Data model decision — payments live on the client doc, not a separate ledger.** Each `clients/{id}` doc holds its own `pago1`/`pago2` fields (`{ amount, status: 'Pendiente'|'Recibido', date: 'YYYY-MM-DD' }`, fixed 60/40 split — constants in `clientStages.js`). This was a deliberate choice over a separate `payments`/`invoices` collection: with only ~10s of clients ever, per-client payment state is simple enough to live inline, and it means the Pagos tab (Clientes) and the Home Finanzas block are reading the exact same fields — no sync step, no drift. If per-client payments ever need to support more than 2 fixed installments, *that's* the trigger to extract a real `payments` subcollection; don't do it preemptively.

**Data model decision — intervention progress lives on the client doc too.** `interventionWeek`/`interventionTotalWeeks` fields on the client, active once `stage === 'intervencion_activa'`. Originally (earlier the same day) there was a separate `interventions` collection referencing `clientId` — retired once it became clear "the intervention" and "the SP's current stage" are the same concept in ADOR's actual mental model, not two things to keep in sync.

**Payment dates are plain strings, not Firestore Timestamps.** `pago1.date`/`pago2.date` are `'YYYY-MM-DD'` strings (set via `<input type="date">`), not `serverTimestamp()` sentinels — these are calendar dates the team enters/edits by hand, not exact server-clock events. `useHomeData.js`'s revenue bucketing reads `payment.date.slice(0, 7)` for the month key accordingly. Don't "fix" this back to Timestamps without checking that call site.

**No Firebase Admin SDK, so no way to list every Auth user from the client** — "Asociado responsable" pickers need a directory. Solved with self-registration: `App.jsx` writes `users/{uid}` (displayName, email) via `saveUserProfile` on every real login (skipped for the `?preview=1` mock user — check `user.uid !== 'preview'` before any write that touches shared collections like `users`, or you'll pollute the real Firestore project with a fake "preview" directory entry, which happened once during testing and had to be manually cleaned up). `subscribeUsers()` in `lib/firestore.js` powers the dropdown.

**Kanban drag-and-drop is hand-built with Framer Motion, no DnD library.** Each `ClientCard` uses `drag` + `dragSnapToOrigin` + `onDragEnd`; `KanbanBoard.jsx` keeps a ref map of each column's DOM node and hit-tests the drop point (`info.point`) against `getBoundingClientRect()` on drop — same pattern already used for portaled dropdown positioning elsewhere in the shell. The SPC→SP conversion glow-pulse fires by diffing each client's stage against a `prevStagesRef` snapshot on every Firestore update, not from the drag handler directly — so it also fires correctly when a stage change happens from the List view's quick-action arrow, not just from a Kanban drag.

**Documentos tab is metadata-only — Firebase Storage isn't enabled.** File name/type/size get written to `clients/{id}/documents`, but no actual file bytes are stored anywhere yet (no Storage bucket configured, unlike Firestore/Auth which went through the same enable-in-console flow earlier this project). The download button is present but disabled with a tooltip explaining why. Enabling Storage (a console step, same pattern as Firestore setup) is the next infrastructure prerequisite before Documentos can be made real — walk the user through it the same way Firestore was set up (see git history / earlier CLAUDE.md revisions for that flow).

**Testing note for future sessions:** simulating real user interaction (hover, blur, drag) via raw `dispatchEvent` calls in this environment is unreliable — React's synthetic event system needs proper `relatedTarget`/focus state that bare `new MouseEvent(...)` often doesn't replicate, and a `.blur()` fired in the same synchronous tick as a preceding `input` event can race React's state update. When verifying forms/interactions here, prefer calling the exported `lib/firestore.js` functions directly via `import('/src/lib/firestore.js')` in the browser console to isolate "does the write work" from "did my simulated event fire" — this saved significant time chasing false-positive bugs during this build.

### 9. Finanzas module (2026-08-14) — asymmetric dashboard, no charting library

Built from a detailed user-supplied UI spec. Lives at `src/components/finanzas/`, wired into `AppShell.jsx` for the `finanzas` nav item — added as a 6th tab on the **top bar** pill-nav (`TopBar.jsx` `PRIMARY_MODULES`), alongside Clientes, not on the sidebar. Layout is a 68%/32% two-column split (`FinanzasModule.jsx`), a deliberate asymmetric composition per the user's spec rather than the shell's usual centered/symmetric card grids.

**Chart is hand-drawn SVG, not Recharts/Chart.js.** The user's spec offered either library, but the project's existing convention (see `FinanceBlock.jsx`'s Sparkline, and README's "No UI component libraries — every control is hand-built") already solved this exact problem without a dependency. `FinanceChart.jsx` follows that precedent: a line+area SVG path animated via Framer Motion's `pathLength`, hover tooltip via mouse-tracked SVG rects, no new package added to `package.json`.

**Ingresos are never a hand-entered monthly total — same source-of-truth rule as Home/Clientes (§7/§8).** `useFinanceData.js` derives "Últimos Ingresos" and the hero "Ingresos del mes" from `clients/{id}.pago1`/`pago2` records marked `Recibido`, merged with a new `incomes` collection that holds *only* manual entries (income not tied to an SP payment — e.g. a one-off consulting fee). Don't reintroduce a parallel collection for SP-payment income; if it doesn't come from a client's pago1/pago2, it's manual and belongs in `incomes`.

**New Firestore collections:** `expenses` (category, description, amount, date, optional `receipt` metadata, notes), `incomes` (manual-only, as above), and a single shared doc `settings/finanzas` holding `quarterlyTarget` (one target at a time, edited inline via the pencil icon on the Meta del Trimestre card — no historical target tracking yet, that's the trigger to add one if it's ever needed).

**Comprobante (expense receipt) is metadata-only, same reason as Clientes → Documentos (§8).** Firebase Storage isn't enabled, so `AddExpenseModal.jsx` stores `{name, type, size}` only — no file bytes. When Storage gets enabled, wire both Documentos and Comprobante uploads together, not separately.

**"Ver todos" on Últimos Ingresos/Gastos expands in place rather than linking anywhere.** There's no dedicated full-ledger page yet; a dead link would violate the spec's own "if it doesn't inform a decision, remove it" instruction. If a full transactions view becomes a real need, that's a separate module/route, not a retrofit of this link.

**Redesigned 2026-08-14 (same day) to match a fintech-dashboard reference image the user shared.** Kept ADOR's own tokens (blue/gold accents, `.ador-glass`, no orange) but adopted the reference's *shapes*: metric numbers became small glass cards with a % badge (`MetricCards.jsx`, replacing the original card-less typography-only hero), the line chart became a bar chart with a highlighted active bar and a floating value bubble (`FinanceChart.jsx`), the two side-by-side 5-row income/expense lists became one searchable, scrollable transactions table with colored status pills (`MovimientosTable.jsx`, replacing `MovimientosBlock.jsx`), and the flat category list became a segmented stacked bar + legend, echoing the reference's "Smart Spending Limits" widget (`CategoryBreakdownCard.jsx`). Two elements from the reference were deliberately **not** ported: the credit-card visual and the "Upgrade Pro" ad card — neither maps to anything ADOR actually needs. The ad card's spot was replaced with `NextPaymentCard.jsx` ("Próximo Cobro" — nearest pending SP payment), which actually informs a decision (who to follow up with) instead of selling an upgrade.

**Firestore rules were not touched by this build — verify them.** This repo has no local `firestore.rules` file (rules are edited live in Firebase Console, per how Firestore was originally set up — see Infrastructure status in `PROJECT_STATE.md`). The `expenses`/`incomes`/`settings` collections were added to `lib/firestore.js` assuming the existing rule (`request.auth != null` AND `allowedEmails/{email}` exists) is a blanket rule covering all collections under `/databases/(default)/documents/{document=**}`. If it's instead scoped per-collection, these three need to be added explicitly in the console before real (non-preview) writes will succeed.

### 10. Workspace module (2026-08-14) — the operational brain, built from a detailed spec

Lives at `src/components/workspace/`, wired into `AppShell.jsx` for the `workspace` nav item. Built from a ClickUp/Monday-style spec the user provided, adapted with judgment calls documented below.

**Intervenciones are never stored — they're derived live from `clients`, same rule as Finanzas/Home (§7/§8/§9).** The spec described "Intervenciones" as one work-group per active SP with its own 8-week duration and 7-layer progress. Rather than create a parallel `interventions`/`workstreams` collection (which CLAUDE.md §8 already documents as tried-and-retired once for this exact concept), `useWorkspaceData.js` derives one virtual workstream per client where `stage === 'intervencion_activa'`, reusing the client's existing `interventionWeek`/`interventionTotalWeeks` fields. Its id is `client:{clientId}`. The current layer (1–7) is *computed* from week/total — there's no `currentLayer` field anywhere. **Proyectos Internos are the only new collection** (`proyectosInternos`) since there's no existing concept for internal firm work; its workstream id is `proyecto:{proyectoId}`. See `lib/workspace.js` for the id convention and the 7 layer names.

**Tasks got a schema change — 4-state status, array assignees.** `tasks/{id}` now holds `workstreamId` (one of the two id shapes above), `assignedTo` (array of userIds, not a single scalar — the spec wanted up to 3 overlapping avatars per task), `priority` (alta/media/baja), and `status` using the spec's 4 states (`por_hacer`/`en_progreso`/`completado`/`bloqueado`) instead of the original 2-state (`pendiente`/`completada`). This is a breaking rename from Home's original task-status vocabulary — `TasksTodayBlock.jsx` and `useHomeData.js`'s fallback were updated in the same change. Safe to do because no real tasks existed yet in production. `subscribeTasksForUser` switched from `where('assignedTo','==',uid)` to `where('assignedTo','array-contains',uid)` to match.

**Decisions got a real write path.** `decisions` already existed (Home's "Última Decisión" read from it) but had no creation UI anywhere — `createDecision()` in `lib/firestore.js` is new. A decision can optionally link to a workstream (`clientId` for an Intervención, `proyectoId` for a Proyecto Interno). Because Home already subscribes to the same collection, decisions registered from Workspace show up in Home automatically — no extra wiring needed.

**Scope cut: Timeline view was not built.** The spec asked for three views (Lista/Kanban/Timeline) toggled top-right. Lista (the spec's own "show me this first" priority) and Kanban shipped — Kanban reuses the exact hand-built Framer Motion drag-and-drop + rect hit-testing pattern already proven in Clientes' `KanbanBoard.jsx` (see §8), just re-targeted at status columns instead of pipeline stages. Timeline (a horizontal Gantt-style week/month view with its own scroll and hit-testing) is a materially bigger, mostly-planning-oriented feature that didn't fit the same pass without either rushing it or shipping something half-built — and per this project's own working rule, a half-finished feature is worse than an absent one. The view-toggle only shows Lista/Kanban for now; add Timeline as its own follow-up rather than bolting a third tab onto the toggle first and filling it in later.

**Scope cut: row-level hover quick-actions (edit/delete icons) were dropped.** The spec wanted them on every Lista row, but clicking a row already opens the Task Detail Panel where edit and delete both live — a redundant hover-revealed icon that does the same thing violates this project's own "nothing decorative, everything earns its place" rule. Delete lives only in the Task Detail Panel, and needs a second confirming click (no native `confirm()` dialog, to stay consistent with the rest of the app's modal-based confirms) rather than firing immediately from a small row icon.

**Priority colors follow the spec's traffic-light scheme (`#EF5350`/`#FFC107`/`#4CAF50`) rather than ADOR's usual blue/gold accents** — this is the one place gold is deliberately absent, since a 3-color severity scale reads faster as red/amber/green than as a blue/gold/gray scale would, and ADOR's own token rules already reserve gold for "decisions/checkmarks only" (§3), not priority.

**Timeline view was added later the same day**, once the user shared a reference image (a Gantt-style board with rounded date-bounded pill bars, a "Now" line, and diamond milestones). `TimelineView.jsx` reuses the reference's *shapes* on ADOR's own tokens: pixel-based date-to-x mapping (not CSS grid) so bars can have exact, comparable widths with horizontal scroll for long ranges; a live "Hoy" line; and diamond markers for tasks with no `startDate` (a real duration needs two dates, and most tasks will only ever get a due date — the diamond is what a 1-day/no-duration task honestly is, not a forced zero-width bar). This requires tasks to carry an optional `startDate` alongside `dueDate` — added as a second date input in the Task Detail Panel, directly beside "Fecha límite". Tasks with no dates simply don't appear in Timeline yet; there's no forced placeholder, consistent with this project's elegant-empty-state rule. The view-toggle now shows all three views (Lista/Kanban/Timeline). The date axis (and "Hoy" line) always renders even with zero dated tasks, defaulting to a 5-week window around today — the empty-state message sits inside the board instead of replacing it, per the user's own follow-up request.

**Empty Workspace shows a real "General" table instead of a blank message.** Originally, zero Intervenciones + zero Proyectos Internos rendered a single centered sentence — the user's follow-up feedback was that this is meant to be the whole company's general workspace, so it needs to look and work like one even before anything's been created. `ListaView.jsx` now falls back to a synthetic `GENERAL_WORKSTREAM` (`{ id: null, kind: 'proyecto_interno', name: 'General' }`) that's never persisted itself — its column headers and "+ Agregar tarea" row render immediately, and the moment someone actually adds a task through it, `InlineAddTask`'s submit handler silently provisions a real "General" `proyectosInternos` doc first, then attaches the task to it. No "create a project before you can even see the board" gate.

**Each group's table got `overflow-x-auto` + a `min-w-[560px]` floor.** Without it, `TaskRow`'s fixed-width columns (avatar stack / priority / due / status) could exceed a narrow Workspace main column and overflow silently — and because an overflowing focused element can force the whole (deliberately non-scrollable, `overflow:hidden`) page to shift horizontally to bring it into view, that overflow was capable of clipping the sidebar and Decisiones panel at the edges of the screen instead of just affecting the table. Confirmed the fix holds by testing down to 1100px width — the table now gets its own local horizontal scrollbar and nothing else on the page moves.

**Lista's rows became a real `<table>` per the user's own follow-up request** ("que se vea como tablas ordenadas"), then got replaced again almost immediately by a CSS Grid version once an actual `<table>` proved unreliable at this row's column count/widths — the Estado column was clipping at moderate viewport widths, an HTML table's per-cell auto-sizing fighting the fixed pixel widths needed for alignment. `TASK_ROW_GRID` (`lib/workspace.js`) is a single `grid-template-columns` string shared by the header row and every `TaskRow.jsx`, so columns are pixel-exact and never renegotiate based on content the way table cells do. Each `WorkstreamGroup` is also now a proper `.ador-glass ador-grain` card (previously just a left-border strip with no background) with a type badge ("Intervención"/"Proyecto Interno") next to the group name — reads as an actual project-management surface instead of a bare list, per direct user feedback that the plain version "no se ve como un sistema de project management." The redundant "Sin tareas todavía" text row was dropped — an empty group with just its header badge and "+ Agregar tarea" already communicates emptiness without a second, weaker echo of the same fact.

**Lista's cells became independently editable, per direct user request ("así como hacen las excelentes plataformas de project management").** Clicking a task's title still opens the full Task Detail Panel, but Asignado/Prioridad/Vence/Estado now edit inline without leaving the row — matching how Linear/Asana/ClickUp handle list-view editing. `CellPopover.jsx` is a small reusable floating menu (portaled to `document.body`, positioned from the trigger's `getBoundingClientRect()` — the same rule as every other floating element per §1) used by `TaskRow.jsx`'s `PillCell` (Prioridad/Estado dropdowns) and `AssigneeCell` (checkbox list); `DueDateCell` just swaps to a native `<input type="date">` in place, no popover needed. Every cell's click handler calls `stopPropagation()` so editing a cell never also triggers the title's "open detail panel" click. Found and fixed a real bug while wiring this up: `CellPopover` originally wrapped its two children in `<AnimatePresence>` without keys, which Framer Motion needs when there's more than one direct child — threw a duplicate-key warning. Fixed by dropping the (unnecessary — the popover mounts/unmounts as a whole via the parent's conditional render, so `AnimatePresence`'s exit-animation coordination wasn't doing anything anyway) `AnimatePresence` wrapper entirely.

**Silent write failures got real error feedback, after the user reported "+ Agregar tarea" as simply not working.** Every create/update call in Workspace (`InlineAddTask`'s submit, and `TaskRow`'s per-cell `applyUpdate`/complete-toggle) previously called Firestore directly with no `.catch` — a failed write (wrong/no auth, rules not yet covering a collection) did nothing visible at all, which reads identically to a broken button. Two fixes, both in `lib/workspace.js`: (1) every write now shows a toast on rejection instead of failing silently: (2) `withTimeout()` races the write against an 8s timer, because a write with no valid auth token attached doesn't always reject promptly — confirmed directly (`await import('/src/lib/workspace.js')` from the console, timing a promise that never resolves) that Firestore can leave such a promise pending indefinitely rather than erroring, which is the more likely real explanation for "nothing happens" than a wiring bug — the click handlers themselves were verified correct by dispatching real DOM events at the exact button. If a write still silently does nothing after this, the next thing to check is whether the signed-in account is in `allowedEmails` and whether Firestore rules cover `proyectosInternos`/`tasks` yet (§9's flagged action item, still open).

**Lista's columns expanded to Tarea/Descripción/Asignado/Prioridad/Estimación/Estado after the user shared a ClickUp-style reference image.** Two additions, both editable inline via the same `CellPopover` pattern as everything else: `description` (new optional string field on tasks — click-to-edit textarea, also added to the Task Detail Panel for consistency) and `EstimationCell`, which replaced the old single-date "Vence" column — it shows `start – due` when both dates are set (falling back to just the due date), editable via a small two-field popover (Inicio/Fin). This reuses the exact `startDate`/`dueDate` fields Timeline already draws bars from (see the Timeline entry above) — setting a duration here is the same duration that shows as a bar there, no separate estimate field invented. `TASK_ROW_GRID` grew to 7 columns to fit.

**Cell editors were extracted into `TaskCells.jsx` and made reusable so the "+ Agregar tarea" row could get every column too, not just a title box.** The user's follow-up on the reference image was specific: the add-row should let you set Descripción/Asignado/Prioridad/Estimación *while creating* the task, matching every real cell in the reference row — not just type a title and fill everything else in after. `PillCell`/`EstimationCell`/`DescriptionCell`/`AssigneeCell` were generalized to take plain values + an `onChange` (no more `task`/`onUpdate` coupling), so `TaskRow.jsx` wires them to `applyUpdate` (writes straight to Firestore) while `ListaView.jsx`'s `InlineAddTask` wires the exact same components to local draft state, only calling `createTask` once when the title is saved. Deliberately **no `onBlur`-triggered submit** on the draft row (unlike the single-field version this replaced) — clicking into any of the other cells blurs the title input, and auto-submitting on that blur would create the task early with whatever partial title existed. Save is Enter-on-title only.

**"Mis tareas" (2026-08-14) — a cross-workstream assignee filter, separate from the workstream selector.** The sidebar previously only let you narrow Workspace to one Intervención/Proyecto at a time; there was no way to see "everything assigned to me" across all of them. `WorkspaceModule.jsx` now holds `onlyMine` alongside `selectedWorkstreamId` — the two are mutually exclusive (selecting a specific workstream turns `onlyMine` off and vice versa, via `selectWorkstream`/`toggleOnlyMine`) rather than combinable, to keep the filter model simple. All three views (Lista/Kanban/Timeline) apply the same `isMine` filter uniformly. Lista/Timeline additionally filter out any workstream left with zero matching tasks (`visibleWorkstreams`), so "Mis tareas" never shows an empty group — and it deliberately does **not** fall through to Lista's own `GENERAL_WORKSTREAM` empty-state card, since inviting "+ Nuevo Proyecto Interno" from inside a personal filter view would be misleading; a dedicated "todo al día" empty state renders instead when the count is zero. The sidebar button shows a live count of open (non-`completado`) tasks assigned to the signed-in user.

**Overdue/due-today tasks now surface in the top bar bell (2026-08-14), the second of three follow-up asks from the same conversation ("Mis tareas" was the first).** `useTaskNotifications.js` follows the exact pattern `useClientNotifications.js` already established (live outside any one module since the bell needs it everywhere, not just while Workspace is open) — subscribes to the signed-in user's own tasks via the existing `subscribeTasksForUser`, flags anything overdue or due today via the same `isOverdue`/`isDueToday` helpers `TaskRow`/`TimelineView` already use, and resolves each task's workstream name by separately subscribing `clients` + `proyectosInternos` and rebuilding the same `client:{id}`/`proyecto:{id}` key shape `lib/workspace.js`'s `workstreamId()` produces (cheaper than pulling in all of `useWorkspaceData`, which also derives Kanban/Timeline-specific groupings this hook doesn't need). `TopBar.jsx` concatenates `useTaskNotifications(user.uid)` ahead of `useClientNotifications()` into one bell list — task deadlines are the more time-sensitive of the two, so they lead.

**Task history (2026-08-14) — the third of the three same-conversation follow-ups.** New `tasks/{id}/history` subcollection, same shape as Clientes' `clients/{id}/history` (§8): `subscribeTaskHistory`/`addTaskHistoryEvent` in `lib/firestore.js` mirror `subscribeClientHistory`/`addHistoryEvent` exactly. Unlike Clientes' Historial tab, there's no manual "log an interaction" form — every entry is auto-generated, because task edits already happen through a small number of known write paths (unlike client interactions, which are real-world events with no natural trigger). The single funnel for that auto-logging is `applyTaskUpdate(taskId, data, actorName)`, new in `lib/firestore.js` — it calls `updateTask` then writes a history line built by `describeTaskChange(data)` (`lib/workspace.js`), which turns a raw patch into a readable summary ("Estado → Completado", "Prioridad → Alta", etc.) by checking which key is present. `createTask` and `toggleTaskComplete` log their own history lines directly rather than going through `applyTaskUpdate`, since "created"/"completed"/"reopened" aren't describable from a data patch alone. **Every task-editing surface now routes through one of these three** — `TaskRow.jsx`'s cells, `TaskDetailPanel.jsx`'s fields, and `KanbanView.jsx`'s drag-and-drop all needed `actorName` threaded in from `WorkspaceModule.jsx` to make this possible, since a history line without an author isn't useful. The Task Detail Panel gained a read-only "Historial" section (`subscribeTaskHistory`) below Asignado, reverse-chronological, matching Clientes' HistorialTab layout minus the input form.

**Zoom levels (Día/Semana/Mes/Trimestre/Año) added right after, same day.** Each level in `TimelineView.jsx`'s `RANGES` map controls three independent things: `pxPerDay` (how zoomed the pixel scale is), `padBefore`/`padAfter` (the default window around today when there's no real task data to size against), and a `ticks()` function — Día/Semana step by calendar day, Mes/Trimestre/Año step by calendar-unit boundary (`startOfMonth`/`startOfQuarter`, stepped via `addMonths`) so labels land on real month/quarter/year lines instead of arbitrary N-day offsets. Real task dates always widen the computed window beyond the granularity's default padding — a task due in 4 months still shows up in Día view, just far down the (scrollable) track, never silently clipped. The board auto-scrolls to center "Hoy" whenever the range or track width changes (a `useEffect` on `scrollRef`), since a track stretched to fit a far-future task would otherwise leave the viewport parked at the far-left edge showing mostly empty space.

**Bug found and fixed while building this: `.ador-grain` was silently breaking every `fixed`-positioned panel that also used it.** `index.css`'s `.ador-grain { position: relative; }` was *unlayered* author CSS, and Tailwind v4's own utilities (`.fixed`, `.absolute`, etc.) live inside a CSS cascade layer — per the Cascade Layers spec, **unlayered rules always beat layered ones**, regardless of source order or specificity. So any element combining `ador-grain` with `fixed` (Task Detail Panel, and the pre-existing Clientes → Ficha `ClientDetailPanel`) was silently forced to `position: relative`, which — for a `fixed inset-0`-backdrop-adjacent slide-in panel sized by `top-0 right-0` — computed to `position: relative` at whatever normal-flow position it fell in, rendering the panel completely off-screen below the viewport instead of sliding in from the right. Confirmed via `getComputedStyle` while wiring up the new Timeline's click-to-open-panel flow. Fixed by wrapping just the `.ador-grain` position rule in `@layer components` so Tailwind's own layered utilities win as expected — see the comment left in `index.css` at that rule. This was a latent, previously-unnoticed bug in `ClientDetailPanel` too, not something introduced by Workspace; worth a quick manual check that Clientes → Ficha still slides in correctly next time it's touched.

### 11. Bug found and fixed across the whole shell (2026-08-15): Chromium drops `backdrop-filter` blur when the same element also has a `transform`

Started as "the notification dropdown looks too transparent" — traced to the *opposite* problem: `NotificationCenter.jsx`'s `motion.div` combined `.ador-glass`'s `backdrop-filter: blur(24px)` with Framer Motion's `animate={{ opacity, y, scale }}`. Chromium has a known bug where an element carrying both `transform` and `backdrop-filter` can stop compositing the blur entirely — confirmed by comparing `getComputedStyle` (backdrop-filter correctly set) against the actual rendered screenshot (background behind it was sharp, not blurred). Critically, this isn't just a mid-animation glitch: Framer Motion leaves an inline `transform: translateY(0px) scale(1)` on the element even at rest once you use explicit `animate={{x/y/scale}}` props (unlike the `layout` prop, which cleans up its transform after a FLIP animation settles) — so the bug persisted indefinitely, not just during the 150ms transition.

**Fix pattern, applied to all 13 affected files:** never combine a transform-animated `motion.div` with a `.ador-glass`/`.ador-modal-surface` class on the *same* element. Split into two nested elements — an outer `motion.div` that owns only the transform/opacity animation, and an inner plain `div` that owns the glass classes and visual content. Affected: `NotificationCenter`, `ProfileMenu`, Sidebar's tooltip, `CellPopover`, all 7 centered modals (`SettingsModal`, `ProfileModal`, `AddExpenseModal`, `AddIncomeModal`, `RegisterDecisionModal`, `NewProyectoModal`, `NewClientModal`), both slide-in panels (`ClientDetailPanel`, `TaskDetailPanel`), and the toast stack (`useToast.jsx`). As a side effect this also fully sidesteps the `.ador-grain`/`.fixed` cascade-layer bug from §10 for the two slide-in panels, since `.ador-grain` no longer shares an element with `.fixed`.

**Overcorrection made and reverted in the same session:** while fixing this, dropdowns/popovers/tooltips were briefly switched from `.ador-glass` to `.ador-modal-surface` (thinking the original "too transparent" complaint meant they needed more opacity). That was wrong — once the blur bug was actually fixed, `.ador-glass`'s normal ~5% tint reads correctly as frosted glass; `.ador-modal-surface`'s ~88% opacity made these elements look like solid black cards, losing the glassmorphism effect entirely. Reverted: `.ador-glass` stays correct for floating dropdowns/menus/tooltips (background should read through, blurred); `.ador-modal-surface` stays correct for centered modals and slide-in panels (deliberately more opaque since they sit above other glass content, per §pre-existing rationale in `index.css`). **If a future floating element looks wrong, check which of these two problems it actually is before changing the opacity class** — a real transform+blur bug looks like "sharp background, no glass effect at all"; the class being merely too transparent looks like "background reads through clearly but text is hard to read against it."

### 16. ADOR IA (2026-08-15) — real Gemini chat, and the project's first backend code

The direction question flagged since §12 ("keyword-matched, zero-cost baseline" vs. "pair with a free-tier LLM for real personality") was resolved by the user: real LLM. Lives at `src/components/adoria/`, wired into `AppShell.jsx`'s existing `ador-ia` placeholder slot.

**This required the project's first server-side code — `api/ador-ia.js`, a Vercel serverless function — and that wasn't optional.** Every other piece of ADOR OS talks to Firebase directly from the browser because Firebase Auth/Firestore are designed for that (client SDK + security rules do the enforcement). A raw API key for a third-party service like Gemini has no equivalent client-side protection: a Vite `VITE_`-prefixed env var compiles straight into the shipped JS bundle, so a `VITE_GEMINI_API_KEY` would be readable by anyone who opens devtools on the deployed site. The serverless function exists specifically to hold `GEMINI_API_KEY` (no `VITE_` prefix, so Vite never bundles it) server-side and proxy the request — the browser posts a message to `/api/ador-ia`, never to Gemini directly.

**Model is `gemini-2.5-flash`** (confirmed via web search at build time — Google's free-tier model lineup changes over the years, so if this ever starts erroring, check the current free-tier model name at ai.google.dev before assuming the code broke).

**Context, not fine-tuning or RAG — same "live-derived, never a stale snapshot" rule as every other cross-module number in this app.** `useAdorIAContext.js` calls the exact same hooks Finanzas/Objetivos/Workspace/Clientes already use (`useFinanceData`, `useObjetivosData`, `subscribeAllTasks`, `subscribeClients`) and `lib/adorIA.js`'s `buildAdorIAContext()` formats the result as a compact, labeled plain-text block (not JSON — reads more naturally as part of a system prompt and costs fewer tokens). This block is re-sent as part of the `systemInstruction` on every single message, so the assistant is always answering from the current state of the business, not a conversation-start snapshot. The system prompt (`ADOR_IA_SYSTEM_PROMPT`) explicitly forbids inventing numbers outside that block — a confidently wrong figure from an "assistant" is worse than "I don't have that data" for a firm handling client-sensitive financials.

**Persona is "trusted chief of staff," not a literal Alfred-from-Batman impression** — the user referenced Alfred as a tone anchor (formal, dry wit, unfailingly competent) during the original scoping conversation, but the system prompt describes those traits rather than claiming to *be* the (trademarked) character.

**Known, accepted limitation: no auth check on the endpoint itself.** `api/ador-ia.js` doesn't verify a Firebase ID token — it trusts that the deployed URL isn't public knowledge, the same posture as the rest of this invite-only tool (no public marketing, no search-indexed pages). If this were ever a real concern, the fix is verifying the client's Firebase ID token server-side (needs `firebase-admin` + a service account, deliberately skipped for v1 scope). The actual exposure today is narrow: someone could burn the free daily quota (1,500 req/day) if they somehow found the URL, not leak data — the endpoint never touches Firestore, it only relays whatever text the client already chose to send.

**Conversation state is ephemeral by design** — messages live in `AdorIAModule.jsx`'s local React state only, no Firestore persistence, resets on page reload. Matches this project's repeated "don't build for a hypothetical" pattern; add a `conversations` collection later if the team actually wants to resume threads.

**Verification note for future sessions:** local `npm run dev` (plain Vite, no `vercel dev`) cannot execute `/api/*` serverless functions at all — a request to `/api/ador-ia` there returns Vite's non-JSON fallback, which `AdorIAModule.jsx` catches and surfaces as an explicit "you're in local dev" error rather than a cryptic parse failure. This is expected, not a bug: real end-to-end testing only happens on the deployed Vercel site, once `GEMINI_API_KEY` is set there.

Given that, the user asked for ADOR IA to still feel as close to "real AI" as possible without any external call. What got built instead, entirely in `lib/adorIA.js` and `AdorIAModule.jsx`, without touching `api/ador-ia.js` or the system prompt (both left intact, ready to reactivate):

- **`answerLocally(question, data, userName, lastTopic)` replaced the Gemini fetch call entirely** — `AdorIAModule.jsx`'s `send()` no longer calls `/api/ador-ia`; it calls this function directly and gets a reply in the same render tick (with a small artificial `setTimeout` delay so it doesn't feel suspiciously instant). Zero network calls, zero cost, works identically in local dev and production — which also incidentally fixes the "local dev can't run serverless functions" limitation from §16, since there's no serverless function in the live path anymore.
- **`computeSignals(data)` is the actual "reasoning" layer** — cross-references objetivos bloqueados, North Star pace vs. `quarterElapsedPct()` (imported from `lib/weeklySummary.js` rather than reimplemented, so ADOR IA's opinion of what's urgent can never disagree with the Resumen Semanal card's), team overload, overdue tasks, stale clients, and cash runway into one ranked list. This is what powers two new cross-module questions — "¿cómo estamos?" and "¿qué debería priorizar?" — that synthesize across all four modules instead of answering one topic in isolation, which is the main thing that makes this feel like more than a keyword-matched FAQ bot.
- **Conversational memory, in-session only.** `answerLocally()` returns `{ text, topic }`; `AdorIAModule.jsx` threads `topic` through a `lastTopicRef` so a short/pronoun-only follow-up ("¿por qué?", "y eso", "detalla", "explica") resolves against whatever was just discussed (`isFollowUp()`) instead of falling into the generic "no tengo ese dato" fallback — the thing that most broke the "conversation" illusion before this. Each signal also carries a `reason` string specifically for "¿por qué?" follow-ups, so asking why something matters doesn't just repeat the same fact back.
- **Alfred-toned phrasing pools (`pick()` helper)** on openers/closers so repeated questions don't read as copy-pasted template output — this was a direct, explicit request ("que sea como Alfred, sofisticado"), not an incidental style choice.
- **Message cap at 50** (`MAX_MESSAGES` in `AdorIAModule.jsx`) — raised by the user asking how to prevent the chat from "sobrecargándose" with heavy use. Since there's no external API anymore, there was never a cost/rate-limit risk to address (explained this directly) — the only real concern left was unbounded in-memory growth over a very long session. Oldest messages quietly drop past the cap; the first time it triggers, a one-time subtle gray line appears above the thread explaining what happened, so it never reads as a bug to whoever notices the thread doesn't scroll back further.
- **If the user ever changes their mind on Gemini:** the fastest path back is restoring `AdorIAModule.jsx`'s `send()` to `fetch('/api/ador-ia', ...)` (see git history around 2026-08-15 for the exact previous version) — `api/ador-ia.js` and `ADOR_IA_SYSTEM_PROMPT` were never touched by this pivot.
